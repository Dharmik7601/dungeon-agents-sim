  ---
  Implementation Plan: Analysis CLI

  What We're Building

  Two standalone scripts that analyze the semantic JSON logs produced by the
  simulation:

  1. src/cli/single_run_analysis.py — deep statistical summary of one run
  2. src/cli/cross_run_analysis.py — aggregate behavioral trends across a
  directory of runs

  Both use rich for output (already a dependency) and operate on the existing
  run_*.json log format. No new dependencies.

  ---
  Log Schema Notes (from inspection)

  Each event has: turn_number, agent_id, action.tool_name, action.arguments,
  execution_result.status, execution_result.error_message,
  execution_result.deltas, state_context.shadow_state,
  state_context.ground_truth, state_context.agent_input.

  The log has no explicit end_condition field — it must be derived:
  - SUCCESS: final ground truth contains exit_unlocked at position X,Y and both
  agent_a_position and agent_b_position equal [X, Y]
  - TURN_LIMIT: last event's turn_number >= 50
  - OTHER (interrupted/deadlock): anything else (run ended early without
  success)

  ---
  Script 1 — src/cli/single_run_analysis.py

  Entry point: python -m src.cli.single_run_analysis --log-file <path>

  Sections printed:

  A. Run Outcome & Duration
  - End state (SUCCESS / TURN_LIMIT / OTHER)
  - Total turns taken
  - If not SUCCESS: Manhattan distance from each agent's final position to the
  exit cell; if the key was never picked up, also distance from agents to the
  key

  B. Agent Efficiency (side-by-side per agent)
  - Action breakdown: count per tool_name
  - Individual error rate: failures / total_actions * 100
  - Chatter volume: count of send_message calls

  C. Delusion Timeline
  - Chronological list of every event with non-empty deltas: Turn N | agent_id |
   property_key | expected → actual | source
  - Time-to-correction: for each delta on a cell_status_X_Y key, scan forward
  through that agent's subsequent events to find the first one where
  shadow_state[cell_status_X_Y] matches the actual_value from the delta. Report
  "corrected in K turns" or "never corrected".

  D. Map Coverage
  - Take the last shadow_state snapshot for each agent
  - Union of all cell_status_* keys across both agents
  - observed / 64 * 100 as percentage

  ---
  Script 2 — src/cli/cross_run_analysis.py

  Entry point: python -m src.cli.cross_run_analysis --dir <path> (default:
  saved_logs/)

  Sections printed:

  A. Global Run Outcomes
  - Total runs parsed, success count + %, avg completion turns (successes only)
  - Failure distribution: TURN_LIMIT vs OTHER

  B. Top Failure Drivers
  - For each failure event: if deltas non-empty → record each property_key; else
   → record the error_message string
  - Output: sorted frequency table of top 5 reasons

  C. Stubbornness Index
  - For each agent, find consecutive same-agent events where both are failures
  AND action.tool_name + action.arguments are identical
  - Stubbornness % = stubborn failures / total failures

  D. Tool Reliability
  - Group all events by tool_name: total executions and total failures
  - Output: table with failure rate % per tool

  E. Average Exploration Density
  - Compute map coverage for each run (same logic as Script 1, Section D)
  - Report mean across all runs

  ---
  Implementation Structure

  Pure computation functions (testable in isolation):
  - derive_end_condition(events) → str
  - compute_agent_efficiency(events) → dict[str, dict]
  - compute_delusion_timeline(events) → list[dict]
  - compute_map_coverage(events) → float
  - compute_stubborn_failures(events) → tuple[int, int]
  - compute_tool_reliability(events) → dict[str, dict]
  - compute_top_failure_drivers(events) → list[tuple[str, int]]

  All take list[dict] (the parsed event list) and return structured data. The
  rendering functions (render_*) call these and format with rich.

  - Unit tests use fixture event lists (small, hand-crafted dicts) — no file

  - main() functions tested with a real saved log file path (smoke test only —
  assert exit 0)

  - No database or persistent storage
  - No CSV/JSON output option (terminal only, per the draft)
  - No filtering flags beyond what's described in the draft plans
